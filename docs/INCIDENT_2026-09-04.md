```
2026-09-04 09:56:55  INFO price refresh: requested=1500 fetched=0 stale_reused=1500 empty=0 failed=0
```

**Zero of fifteen hundred symbols downloaded. The run reported `failed=0`.**

|---|---|---|
| 09-01 | 1280 | 220 |
| 09-02 | 1218 | 282 |
| 09-03 | 1258 | 242 |
| **09-04** | **0** | **1500** |

Every call raises the same thing, including a single ticker fetch of SPY:

```
WARNING yfinance history fetch failed for SPY: 'NoneType' object is not subscriptable
ERROR [...200 symbols...]: TypeError("'NoneType' object is not subscriptable")
```

That is not throttling. Throttling returns a rate limit error. A `NoneType` on

what happens when Yahoo changes the endpoint shape and the installed client is
behind. `requirements.txt` line 8 pins `yfinance>=0.2.50`, an open upper bound,
so the installed version is whatever conda last resolved.

## The guard that must ship with this fix

This incident was survivable only because nobody traded on it. It must never be
silent again.

`data/price_cache.py`, `refresh_prices`:

1. A symbol whose download raised is counted in `rep.failed`, **even when a
   stale cache exists to fall back on**. Stale reuse is a degraded outcome, not
   a success.
2. `DataQualityReport` gains `stale_age_days` per symbol.
3. `refresh_prices` raises when the fetched fraction falls below a floor
   (start at 50%). A run that fetched nothing must not proceed to build a book.
4. `scripts/oros_run.py` catches that and sends the same loud alert email the
   workflow sends on failure, then exits non zero.

Point 3 is the whole lesson. Today the system had no market data at all and
still emailed nothing, journaled a book, and looked from the outside like a
quiet day.

# UPDATE, later on 2026-09-04: it is rate limiting, not only a stale client

A direct HTTP probe of Yahoo from a network path on the Mac returns **429 Too
Many Requests**, repeatedly, on both hosts:

```
query1.finance.yahoo.com/v8/finance/chart/SPY   HTTP 429
query1.finance.yahoo.com/v8/finance/chart/AAPL  HTTP 429  (x3)
query2.finance.yahoo.com/v8/finance/chart/MSFT  HTTP 429
```

Not a connection failure. Not a parse failure. Yahoo is throttling.

**Caveat before acting on this:** that probe ran from the desktop workspace VM,
whose egress may not be the same path conda python uses. Confirm from the real
shell first. See step 0 below.

## Why this is the better explanation

An older yfinance does not surface a 429 as a rate limit. It gets a body it
cannot parse and downstream code indexes into None, producing exactly the
`'NoneType' object is not subscriptable` seen on every symbol.

And the stale counts were climbing for days before today's total failure:

| Date | fetched | stale | reading |
|---|---|---|---|
| 09-01 | 1280 | 220 | partial throttling |
| 09-02 | 1218 | 282 | worse |
| 09-03 | 1258 | 242 | worse |
| **09-04** | **0** | **1500** | fully blocked |

That is a quota being consumed, not a client that broke overnight.

## The request volume behind it

Per weekday, against a free unauthenticated endpoint, from one address:

```
09:35  cron        1500 symbols
10:20  watchdog    1500 symbols   (fires because it sees no cloud journal)
17:50  watchdog     500 symbols
       cloud runs, Scan Now clicks, Streamlit sessions, manual runs
```

Roughly 3500 symbol requests a day, and the watchdog duplicates the cron run in
full. That duplication is the same defect as the duplicate book problem: the
fallback is not free, it doubles the quota burn.

## Fix, in order

### 0. Confirm from the real shell first

```bash
curl -sS -o /dev/null -w "%{http_code}\n" "https://query1.finance.yahoo.com/v8/finance/chart/SPY?range=5d&interval=1d"
```

* **429** confirms rate limiting. The upgrade alone will not fix it. Do 1 and 2.
* **200** means the probe path differs from python's, and this is a client
  version problem after all. Do 1 only.

### 1. Upgrade the client so a 429 is reported as a 429

Current yfinance is **1.7.0**. `requirements.txt` floors at `0.2.50` with no
upper bound, so a 0.2.x install is plausible and that is a major version behind.

```bash
source /Users/jpromero/anaconda3/bin/activate && conda activate dev2
python -c "import yfinance as yf; print(yf.__version__)"
```

**Expect breakage on a 0.2 to 1.x jump.** `yf.download` column shapes and
`auto_adjust` defaults changed, and `price_cache._normalize` has already been
bitten once by a yfinance shape change (see the comment about a single ticker
batch returning a tuple). Do the upgrade in a throwaway env first, or be ready
to fix `_normalize`. A smaller first move is the newest 0.2.x.

### 2. Cut the request volume, which is the actual cause

1. **Stop the watchdog full refresh.** It re-fetches all 1500 symbols the cron
   already fetched an hour earlier. It should reuse the cron's cache, or check
   for a journal and exit, not rerun the pipeline.
2. **Lower `OROS_REFRESH_CAP`.** 1500 daily against a free endpoint is the
   problem. The scan cap is 500; refreshing 1500 to scan 500 is waste.
3. **Backoff on 429 specifically.** Detect the status, sleep, retry with
   escalating delay, and if it persists, fail loudly rather than silently
   serving stale bars.
4. **Use the paid keys already in `.env`.** `ALPHA_VANTAGE_API_KEY` and
   `FMP_API_KEY` are configured. A commercial product on a free scraped
   endpoint has no delivery guarantee and no data licence. This is also the
   market data licence blocker already on the commercial launch list.

### 3. It may clear on its own

Yahoo throttles usually lift after a cooldown. If step 0 returns 429, wait an
hour, probe again, and do not hammer it meanwhile. Every failed run deepens it.
