# INCIDENT 2026-09-18 — the morning scan produced nothing and said it was fine

Status: **fixed and tested**. Read this before touching the refresh path.

---

## One-line cause

On some mornings the Mac has **no DNS resolver** when the launchd job fires,
and `refresh_prices` counted every failed symbol as a *stale-cache success*,
so a run with **zero market data** reported `failed=0`, graded 500 charts on
bars that had not moved, and journaled a book.

---

## The evidence

Fourteen September cron logs. `fetched` is from the `price refresh:` line,
`dns` counts `Could not resolve host`.

| 09-01 |  0 | 1280 | 09:35:04 |
| 09-02 |  0 | 1218 | 09:35:00 |
| 09-03 |  0 | 1258 | 09:35:04 |
| 09-04 | 60 |    0 | 09:49:50 |
| 09-07 |  0 | 1227 | 09:35:03 |
| 09-08 |  0 | 1223 | 09:35:03 |
| 09-09 | 62 |    0 | 09:37:29 |
| 09-10 |  4 |    0 | 09:50:38 |

**dns > 0 ⟺ fetched = 0. No exceptions in 13 observations.**

Every clean day started at 09:35:0x. Every dead day started late, which is
what a launchd `StartCalendarInterval` does when the machine was asleep: it
fires the missed event at WAKE, before the network stack is ready. The run
then spent 29 minutes against a dead resolver.

The sqlite `unable to open database file` noise appears on healthy days too
(3 per run), so it is **not** the discriminator. It was a red herring.

### The artifact that proves the damage

`stage_breadth.json` for 2026-09-18 and 2026-09-16 were identical, down to
the scan hash:

```
2026-09-16  total 500  {Advancing 206, Basing 184, Topping 21, Declining 89}  hash 1f8f65631daba214
2026-09-18  total 500  {Advancing 206, Basing 184, Topping 21, Declining 89}  hash 1f8f65631daba214
```

Today's "market breadth" was Monday's, verbatim, because every price was
stale. The 09-18 scan artifact records `stale_rows: 500` of 500. Any book,
score or backtest touching these days is reading the same day twice.

### Why nobody was told

`ml/daily_report.py` wrote the PDF, then `send_email` failed with
`[Errno 8] nodename nor servname provided` — the same dead resolver. The
run exited `0`. From the outside: a quiet day.

---

## What was actually wrong in the code

1. **No connectivity gate anywhere.** Nothing asked whether a resolver
   existed before spending 29 minutes.
2. **`refresh_prices` mis-counted failure.** A symbol whose download failed
   was recorded as `from_stale` and `from_stale` was not a failure. Hence
   `fetched=0 stale_reused=1496 failed=0`.
3. **The return value was discarded.** `scripts/oros_run.py:135` called
   `price_cache.refresh_prices(work)` and ignored the report entirely.
4. **The watchdog opted out of its own job.** On a `git fetch` failure it
   logged `standing down, no local fallback` and exited 0 — so the one
   component built to catch a failed morning skipped the morning that failed.
5. **A full 2-year re-pull for 1500 names every weekday**, to scan 500.

---

## The fix

### `data/netcheck.py` (new)
DNS preflight with bounded exponential backoff. Strict: **every** host must
resolve, because a morning that reaches Yahoo but not the mail server is a
scan nobody receives. `OROS_NET_HOSTS` overrides the list.

### `data/price_cache.py`
* A failed symbol lands in `failed` **whether or not** a stale cache exists.
  `degraded` records the reuse separately. Stale reuse is degraded, not success.
* `DataQualityReport` gains `recovered`, `throttled`, `transport_fault`,
  `max_stale_age_days` and `fetch_fraction`.
* **Incremental window**: a cache younger than 10 days is topped up with a
  1-month pull and merged, instead of re-pulling 2 years. Cold and stale
  symbols still get the full period.
* Throttle-aware backoff, exponential rather than linear. An empty bulk frame
  is treated as a retryable failure, not as "no such symbol".
* `min_fetch_fraction` raises `DataFeedError`. Defaults to `None` so the ~20
  interactive callers keep their forgiving behaviour.
* yfinance's sqlite tz cache is pinned to `~/.cache/oros/yf_tz` with a temp
  fallback. It must **not** live in the repo: on a synced or network-backed
  volume sqlite degrades to `disk I/O error` / `database is locked`, which was
  reproduced during this fix.

### `data/stooq.py` (new)
Failover daily OHLCV, no API key. **Only** consulted for symbols Yahoo
refused, so a healthy morning makes zero Stooq requests and the two feeds can
never disagree inside one run. Abandons after 5 consecutive faults so failover
can never become a second outage.
*Licensing: this closes the availability gap, not the licensing one. A paid
product still needs Tiingo / Polygon / Nasdaq Basic.*

### `scripts/oros_run.py`
* Preflight runs **above** the edition branch, so the Closing Bell is gated
  too. (First attempt put it inside the morning branch and left the evening
  path completely ungated.)
* Refresh is called with `min_fetch_fraction` and `DataFeedError` is caught.
* New exit codes: **3 = no network**, **4 = no fresh market data**. Both
  abort before anything is scanned, journaled, emailed or published.
* `--min-fresh` (`OROS_MIN_FRESH`, default 0.60), `--net-wait`
  (`OROS_NET_WAIT`, default 900), `--skip-preflight`.
* Fixed a latent bug: a local `import os as _os` inside `main()` made `_os`
  local to the whole function.

### `scripts/oros_cron.sh`
Retry ladder: 3 attempts, 15 minutes apart, **only** on exit 3 or 4. A wake
at 09:42 with a network that returns at 10:05 now still delivers. The abort
alert is suppressed on every attempt but the last — one email per failed day,
not one per attempt.

### `scripts/oros_watchdog.sh`
Waits for the network instead of standing down on a failed `git fetch`.
"Offline" is a temporary state, not a verdict. If the network genuinely never
returns it stands down and says so loudly.

## Tests

`tests/test_data_feed_guards.py` — 19 tests, no network:

* total outage reports `failed=3`, not `failed=0` (**the regression**)
* `DataFeedError` raised below the floor, not raised when the floor is `None`
* throttle and transport faults classified and flagged
* an empty bulk frame counts as failure
* warm cache tops up, cold cache pulls full, merge never truncates history
* Stooq CSV parsed, block pages and `No data` rejected, symbol mapping,
  429 raises, failover abandons after repeated faults and can lift a run
  back over the floor
* `wait_for_network` returns when the resolver comes back, raises on timeout,
  and requires every host

Verified live as well: exit 3 on a bogus host, exit 4 below the floor, the
3-attempt ladder with exactly one alert email, a 500-name incremental refresh
at `fetched=500 failed=0 fresh=100.0%` in 63s, and journal counts unchanged
across every abort.

## Operating notes

* `OROS_REFRESH_CAP` is still 1500 to scan 500. The incremental window makes
  that far cheaper, but refreshing three names to grade one is still waste.
  Consider 800.
* **The evening edition is not idempotent.** Running it twice publishes two
  public YouTube videos and sends two emails. There is no "already published
  today" guard. Same class as the duplicate-order problem in the execution
  notes. Not fixed here.
* Days 09-04, 09-09, 09-10, 09-14, 09-17 and 09-18 were graded on stale bars
  and should be excluded from any scoreboard or backtest.
